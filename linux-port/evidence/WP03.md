### Seams introduced (only where `android.*` forced it)

- **`KeyMaterial`** (`com.relay.app.crypto`, core): `encryptTo(recipientKey, plaintext)` / `decryptMine(ciphertext)`.
  `InnerEnvelope.seal/open` take it explicitly. App side: `AndroidKeyMaterial(context)` over `RelayCrypto`, and
  `AndroidInnerEnvelope` (same shape as the old `InnerEnvelope`, so the `InnerEnvelope::seal` function references in
  `Outgoing`/`GroupDispatch` only changed name).
- **`NostrSigner`** (`com.relay.app.transport.mailbox`, core): `signEventJson(kind, content, tags): String`. `MailboxAuth.header`
  and `MailboxMedia` take it. App side: `AndroidNostrSigner(keys: () -> Keys)`. **The keys are resolved at signing time**,
  exactly where the old call sites resolved them (matters for `MailboxMedia.confirm`, which swallows failures inside `runCatching`).
  `:core` therefore has **no rust-nostr dependency**; the `MailboxAuth` class is now public (it was `internal`).
- **`MailboxConfig.install(url)`** replaces `BuildConfig.MAILBOX_URL`. `RelayApplication` calls it from an `init {}` block
  (the Application constructor, which runs before any provider/service/receiver).
- **`HttpTransport` was NOT introduced.** `MailboxMedia` only needed `Context` for keys; its OkHttp 4.12.0 client is plain
  JVM and the same version `:app` already uses, so no interface was needed. Add it in WP06 if the desktop wants to inject sockets.
- `android.util.Base64` → `java.util.Base64` in `InnerEnvelope` (`NO_WRAP` = `getEncoder()`) and `MailboxAuth`. Everything else
  moved already used `java.util.Base64`. `org.json` is `compileOnly` in `:core` (the Android platform provides it, so `:app`
  does not package a second copy; verified below) and `testImplementation` for tests (as `:app` already did).

## AC2 — golden corpus — PASS

`core/src/test/kotlin/com/relay/app/golden/BodyCodecGoldenTest.kt` records `core/src/test/resources/golden/body-codecs.golden`:
**328 entries** (sha256 of the file recorded by the final run: see the end of this file), covering `PayloadCodec`, `MediaBody`,
`ProfileNameBody`, `ProfilePhotoBody`, `ReplyBody`, `DeletionBody`, `PurgeBody`, `ReadReceiptBody`, `ConversationEventBody`,
`TypingBody`, `GroupAvatarBody`, `GroupProtocol` (sync + all five event kinds + roster/verdict rules), `SmsMessageParser`,
`IncomingClassifier`, `PairingMessages`/`PendingPairing`, `QrContactCode`, `InboxRelays`, `MailboxProtocol` (frames, requests,
outcomes), `MediaContainer`, `MediaCrypto` (fixed-key decrypt vectors; encryption is random so only round-trip/size) and Base64
vectors. 34 entries record the *failure* of a hostile/invalid input (`throws:…`/`null`).

Recording: written with `RELAY_GOLDEN_RECORD=1` in a **pristine `git worktree` of `1081c5a`** (nothing moved, nothing edited;
only the test file overlaid), in the `:app` test source set, against the original `:app` classes. The test was then moved to
`:core` and run in compare mode post-move. The recorder was first run twice on the working tree (byte-identical output, so the
corpus is deterministic) and once more in the pristine worktree after `TypingBody` entries were added (first 317 entries identical).
Mutation checks (restored byte-for-byte, `cmp` verified): changing `GroupProtocol.VERSION` 2→3 fails
`bodyCodecsAreByteIdenticalToTheRecordedCorpus`; switching `MailboxAuth` to URL-safe Base64 / kind 27236 fails two `MailboxAuthTest` cases.

Not recordable bit-for-bit (randomised): HPKE ciphertext, AES-GCM key/IV, NIP-98 nonce and Schnorr signature. These are covered
structurally (`InnerEnvelopeTest` with RFC 4648 vectors and a fake `KeyMaterial`; `MailboxAuthTest` with a recording signer).

**Important caveat:** the corpus is recorded under `org.json:json:20240303` (a `HashMap`), the artifact `:app`'s JVM tests already use.
Android's platform `org.json` keeps insertion order, so JSON key order in bodies **on a phone differs from the golden strings**
(both are valid for receivers, which read by key; this difference existed before WP03 and is not changed by it). The desktop
must not assume key order either way; a cross-implementation byte-order test needs an on-device recording.

## AC4 — two-emulator harness — NOT RUN

A separate **single-emulator** actual-app UI/Worker smoke was run after the extraction (not AC4; it exercises one
device against a local Worker). Two earlier attempts failed at `JvmAppInteropTest.kt:60` (`Visible 2`) and then at
JVM reply verification. Root cause was **the harness invocation, not the product**: those runs launched the AVD with
`-skin 480x800`, overriding the AVD's own 1080x2400 @ 420dpi configuration, and the clipped layout hid the calculator
keypad from UiAutomator. Re-running on the same AVD at its native resolution passed end to end:
`OK (1 test)`, production calculator unlock → chat UI → production outbox → `MailboxTransport` → local Worker →
JVM NIP-17/HPKE decrypt → real composer reply decrypted by the JVM peer. Safe artifacts:
[chat.png](wp03-app-ui/chat.png), [passed.json](wp03-app-ui/passed.json), [ui-sent.json](wp03-app-ui/ui-sent.json)
(test-only contact "JVM Spike"; no keys, SDP or personal data).

Supporting harness fixes made during that diagnosis: the WP01 spike's JVM and Android test source sets now read
`RelayPayload.kt` from its new `core/` location (`:jvm:test :jvm:installDist` pass), and `run-app-ui.py` matches the
installed main package as a whole line so an installed `com.relay.app.test` package is never mistaken for protected
main-app data. Six ownership/source-path guard tests pass. The disposable fixture was cleared only after its exact
ownership marker was read back; the emulator was stopped afterwards.

Blockers for the separate **two-emulator AC4 harness** (it was not started):
- `rebuild/dev/test-mailbox-emulators.py` needs **two emulators at the same time** (Alice `emulator-5554`, Bob `emulator-5556`). The
  terminal cgroup is about 4 GiB; one emulator at a time is the safe limit, and `adb devices` showed none running.
- It builds against `.local/mailbox.properties` and **talks to the live pilot delivery server**; its `--deploy-allowlist` path runs
  `wrangler deploy`. The WP04 agent is concurrently editing `server/cloudflare/**`, so a live run now would test an unrelated moving target.
- The harness also needs a "before" run on the unmodified app for comparison.

What would be run: build the debug APK + androidTest APK on the `1081c5a` baseline and on this tree, install on both emulators, run the
harness for pairing, text, photo, and the group post/photo steps, once each. **R1 (09) therefore remains only partly mitigated**:
the byte-level protocol is pinned by AC2, and the seams are the same code paths, but no on-device flow was exercised.
Specific unrun risk: `MailboxConfig.install` in `RelayApplication`'s constructor (an empty URL would silently disable the mailbox
transport), the lazily-resolved `AndroidNostrSigner`, and the Android runtime using the platform `org.json`.

## What stayed in `:app`, and why

- `RelayCrypto` (+ `RelayFileCrypto`): Android Keystore/`AndroidKeysetManager`/SharedPreferences throughout. Its Tink primitive calls are
  reached only through `KeyMaterial`; moving them would make `:core` depend on Tink and change `:app`'s Tink 1.23.0 to the desktop's
  1.24.0 (a behaviour change). **Deliberately deferred**: the desktop supplies its own `KeyMaterial` in WP06 (probe: JVM Tink 1.24.0 works, WP01).
- `MailboxTransport`, `MailboxPush`, `MailboxMembership`, `MailboxStore`, `NostrTransport`, `NostrIdentity`, `Transports`, `TorControl`:
  Android `Context`, rust-nostr `Keys`/`NostrSigner`, `BuildConfig`, Firebase, WorkManager. (Android depends on `nostr-sdk-kmp-android`; the JVM spike on `-jvm`.
  Only the Kotlin SDK API is shared, so the shared surface is expressed with `NostrSigner` instead of an SDK dependency.)
- `TypingSignals`, `MessageDeletion`, `GroupDelivery`, `GroupDispatch`: the pure codec/presence part of `TypingSignals` moved; the others are
  databases/`Context`/notifications with no separable decision left. `GroupProtocol` already holds the roster rules.
- `p2p/*` (`P2pOffer`, `P2pWire`, `PresenceCore`) and `OutboxDispatch`: not in 04 §2; not examined for purity; candidates for a follow-up slice.
- `ConversationFormat`, `ChatTimeline`, repositories, db: UI/SQLCipher.
