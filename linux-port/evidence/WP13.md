## Host contract → Android implementation

Binding requirements from `CALL_ENGINE.md` and where they are met:

| Contract | Implementation |
|---|---|
| `ClockPort` is wall-clock epoch ms | `WallClockPort.nowMs() = System.currentTimeMillis()` |
| `RandomPort` is cryptographically secure | `SecureRandomPort` over `java.security.SecureRandom` |
| One serial context for dispatch/onWire/port callbacks | `CallController.dispatcher` (single-thread executor); timers, TURN, and WebRTC reports all post onto it |
| First `invite` = `LIVE_AND_STORED_URGENT` | `MailboxSignalPort.send`: socket `signal` frame **and** `MailboxTransport.deliverUrgent` |
| Stored invite opened like a live one; `EXPIRED` enforced by the engine | `IncomingMessageHandler.handle` → `CallController.onStoredDelivery` → `CallRuntime.onWire` |
| Filter senders before `onWire` | `CallHostCore.onWire`: only self or an allowed (QR-verified, non-blocked, non-deleted) contact |
| `OpenPeerConnection` is the first thing that opens the mic | `WebRtcPeer.open` creates the audio source/track; nothing opens the mic earlier |
| `ClosePeerConnection` releases the mic once | `WebRtcPeer.close` is idempotent; `CallTeardown` guarantees one teardown per call |
| Cancel the in-flight TURN request when the call ends | `MailboxTurnPort.cancel` + a call-id check that drops stale answers |
| Effects applied in order, `StateChanged` last | `CallRuntime` orders the effects. **Correction:** the original `MailboxSignalPort.send` launched one independent coroutine per effect, so on the wire a cancel could overtake its invite; sends are now serialised per recipient (`RecipientSignalQueue`) and tested through the real `MailboxSignalPort` (`mailboxSignalPortDoesNotLetCancelOvertakeABlockedInvite`). Earlier text claiming “the host never reorders” was false for the wire. |
| `Ended` is sticky; a new call starts from it | Not reset: the host keeps the same runtime. **Correction:** this was previously asserted but untested; `startCallIsAcceptedFromEndedAndGetsAFreshCallId` now covers it |
| Busy from one callee device is not terminal | The engine handles it; host tests assert a second invite gets `busy` without ending the live call and that dialing during a call is rejected (`dialingDuringALiveCallIsRejectedAndLeavesTheCallRunning`) |

## How RED was obtained (honest account)

The pure-decision tests were written before the Android glue, but not every one produced a first-run
failure. The first focused run was **46 tests, 42 passed, 4 failed**: three failures were test-side mistakes
(a reused nonce made the answered-elsewhere packet replay-rejected; two assertions ignored the ringing hint
that follows an incoming invite) and one was a real implementation bug (`maxaveragebitrate` was emitted as
`32` instead of `32000`). Those four are **not** presented as clean RED for the other 42.

RED for the remaining behaviours was established by **mutation checks**, applied one at a time to the
production source, with the focused test run and the source restored afterwards (and the full suite re-run
green after restoration):

## Deliberate deviations and open items

1. **No `androidx.core:core-telecom` / `ConnectionService` self-managed registration.** The dependency is not
   on the classpath, and registering a `PhoneAccount` needs a real device to verify. This pass implements the
   documented simpler equivalent: `CallForegroundService` with `phoneCall|microphone` types, audio focus and
   communication mode, CallStyle notification, full-screen intent (when allowed), and a proximity wake lock
   on earpiece. Consequence: no interaction with cellular calls and no wearable/Bluetooth “system call”
   routing beyond `AudioManager.setCommunicationDevice`. WP13 step 2 is therefore **partly** implemented.
2. **WebRTC version.** `io.github.webrtc-sdk:android:144.7559.15` (AAR sha256
   `fc7c8d027eb33860ccbb7847988f7f942d44a92d1f575348bba6c0250cde4071`) is what the call spikes pinned and what
   the local Gradle cache already had. WP13's planning note names `150.7871.04`; that version was not fetched,
   because fetching a new artifact would need network access and (in a repo with dependency verification)
   regenerated metadata, and no `verification-metadata.xml` exists here.
3. **FCM urgent path reuses the transport's own catch-up.** `onUrgentWake` calls
   `MessagingRuntime.ensureStarted` + `onForeground`, which connects the socket immediately; the socket's
   catch-up delivers the stored invite to the call host. This bypasses `PollWorker` as 06 §4 requires, but
   there is no separate bespoke “fetch the inbox” implementation. One code path for messages and calls is
   deliberate; it is also why no latency number is claimed.
4. **“Previews hidden” maps to the existing notification setting.** There is no dedicated call-preview pref;
   when `incomingMessageNotification` is off (or the install is calculator-only) the notification shows the
   generic label “Relay call” (`callNotificationName`, unit-tested). **Correction:** the original notification
   was `VISIBILITY_PUBLIC` and so showed the name on the lock screen even with previews hidden; both call
   notifications and the channel are now `VISIBILITY_PRIVATE`. The lock-screen appearance itself is NOT RUN on a device.
5. **Socket upgrade still says `device=primary`.** Pre-existing (`MailboxTransport.socketUrl`). Call bodies
   carry their own `device` field, so call routing/`to` filtering is unaffected; the cursor identity is a
   separate pre-existing issue and was not changed here.
6. **`Always relay calls` takes effect at the next process start**, because `CallHost` reads the pref when it
   is assembled. The toggle says so in its supporting text.
7. **Linked-device answering** is a protocol-level feature (LP-D10). This phone is `primary`; the engine's
   accept-race/`answered_elsewhere` logic is exercised in JVM tests, but no desktop peer exists in this
   session, so the cross-device stop is **unit-verified only**.
8. **`CallController.isBusy()` reads engine state from any thread.** The gate check tolerates a stale read
   (the engine itself rejects a second `StartCall`); no lock is taken on that path.
