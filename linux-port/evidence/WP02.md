## Actual encrypted signal sizes (parent addition)

Record the **real** offer, answer and gathered ICE as proposed call bodies privately, then encrypt them using
WP01's Tink HPKE + production `RelayPayload` codec + NIP-17 gift wraps, serialize the mailbox `signal` frame, and
unwrap/decrypt each one again to assert round-trip equality. Synthetic sender/receiver keys only; body files remain
in ignored `.local/`, and output contains only sizes. The fixed metadata is a measurement schema, not the finished
call authorization protocol.

```sh
mkdir -p .local/wp02-bodies
chmod 700 .local/wp02-bodies
RELAY_SPIKE_BODY_DIR="$PWD/.local/wp02-bodies" timeout 120 ./gradlew \
  -p linux-port/spikes/calls --no-daemon -Dorg.gradle.java.home="$JAVA_HOME" \
  --dependency-verification strict --rerun-tasks probe
./gradlew -p linux-port/spikes/jvm-transport --no-daemon \
  -Dorg.gradle.java.home="$JAVA_HOME" --dependency-verification strict \
  --rerun-tasks :jvm:test :jvm:installDist
linux-port/spikes/jvm-transport/jvm/build/install/jvm/bin/jvm measure "$PWD/.local/wp02-bodies"
```

Observed size rows (bytes):

| Kind | Plain call body | Inner `TYPE:ENC` | NIP-17 envelope | Whole signal frame |
|---|---:|---:|---:|---:|
| Answer | 1,712 | 2,368 | 7,333 | 7,462 |
| ICE batch | 4,172 | 5,648 | 14,161 | 14,290 |
| ICE batch | 4,952 | 6,688 | 14,161 | 14,290 |
| ICE batch | 1,436 | 2,000 | 5,969 | 6,098 |
| Offer | 1,716 | 2,372 | 7,333 | 7,462 |

`Mailbox.relaySignal` bounds the UTF-8 **envelope**, not the entire JSON frame. All five real encrypted specimens
fit the current **16,384-byte envelope limit**, and the largest whole frame also fits the proposed 14 KiB target.
**Decision: leave MAX_SIGNAL_BYTES unchanged.** NIP-44 padding creates steps, so a larger candidate batch,
IPv6/TURN candidate, metadata change or SDK update may jump sharply. This sample is not a proof for every future
packet. WP11/WP12 must enforce the final serialized byte limit and split candidate batches by bytes, not merely by
20 candidates. Rerun the test with Android-generated SDP/candidates and actual production call metadata before
closing the final signal-size gate.

The reused WP01 JVM suite was executed again with strict verification and `--rerun-tasks`: **5 tests, 0 failures,
0 errors, 0 skipped**. This commit changes its runner only to add `measure`; that integration belongs to WP02.

## Dependencies / practical findings

- Desktop `dev.onvoid.webrtc:webrtc-java:0.20.0` with explicit `linux-x86_64` classifier and `transitive=false`:
  upstream classifier self-dependency otherwise caused a resolution stall. Both native and API jars are pinned.
- Android probe pins `io.github.webrtc-sdk:android:144.7559.15`, **not** the planning candidate 150.7871.04. This is
  the artifact actually exercised, not approval to ship an older native engine. Final SDK pin/security review and
  cross-version negotiation remain gates. AGP 8.3.2 warns about compileSdk 36 (tested through 34); no warning was
  hidden and no root plugin was changed.
- Explicit disposal of native channel, track, sender, receiver and transceiver references is required for clean
  JVM shutdown. Two earlier delegate runs and both parent runs terminated normally after the fix.
- Independent verification XMLs are new: desktop **2 components / 4 SHA-256 entries**, Android **180 components / 304 SHA-256 entries**;
  root verification metadata unchanged. Exact artifact hashes and native licence inventory are in the
  [desktop audit](../spikes/calls/evidence/dependency-audit.json) and
  [Android audit](../spikes/calls/evidence/android-dependency-audit.json).
  Native redistribution licences remain unapproved; these are development probes, not release artifacts.
