## 1. What was incomplete and what changed in this pass

The previous agent left a working module but three real defects and one missing acceptance proof:

1. **The SQLite file was not `0600`.** `DesktopPaths.secureDirectory` made the directory `0700`, but
   SQLite creates `relay.db` (and `-wal`/`-shm`) with the process umask (usually `0644`). Fixed in
   `DesktopMessageStore` with `secureFiles()`, called after open/migrate and after each commit that can
   create or replace a sidecar.
2. **The packaged app could not start.** `jpackage`'s suggested module set omitted `java.sql`, so the
   app image died with `NoClassDefFoundError: java/sql/Connection` before the window existed. Fixed by
   adding `modules("java.sql")` to `nativeDistributions`; verified by launching the packaged app.
3. **The E2E test could not use the requested persisted Worker state.** It always used
   `Files.createTempDirectory`. Added an optional `RELAY_E2E_PERSIST` (default stays a temp dir) and
   printed the path in its success line, so the evidence run uses `.local/wp06-worker-state`.
4. **Weak encryption assertions.** The existing "not plain SQLite" test only checked the 16-byte header
   and the WAL. Extended it to scan the **whole database file** for a message sentinel (the WP06
   requirement), and added a separate `0600` mode test. No test was deleted or weakened.

## 3. Encryption evidence

### 3.1 Tests (all pass)

`DesktopMessageStoreTest`:

- `database file is not plain SQLite and wrong key fails`
  - header is **not** `SQLite format 3`;
  - the **entire** `relay.db` byte stream does not contain the sentinel `top secret text`;
  - opening the same file with a different `FileSecretStore` key throws `SQLException`. (The key is a
    passphrase to SQLCipher's KDF, so a wrong key fails the first page check.)
- `database file is owner-only 0600` — `relay.db` is `0600`; if present, `relay.db-wal` and
  `relay.db-shm` are `0600` too.
- `wal file does not contain message plaintext` — the WAL does not contain `PLAINTEXT-SENTINEL-12345`.

### 3.2 Modes on a real run

The packaged app was started with `XDG_CONFIG_HOME=.local/wp06-ui/config` and
`RELAY_FORCE_FILE_SECRET_STORE=1`; after it created its state:

```
600 143   identity.json
600 504   keymaterial.json
600 4096  relay.db
600 32768 relay.db-shm
600 37112 relay.db-wal
600 44    secret.key
```

`identity.json` contains only `{"v":1,"sealed":"…"}`; the Nostr secret is AES-256-GCM-sealed with the
secret-store key. `keymaterial.json` is likewise sealed Tink keyset JSON (the test also asserts the raw
file contains neither `primaryKeyId` nor `keyData`).

### 3.3 Driver and licence

The store is opened by **`io.github.willena:sqlite-jdbc:3.50.1.0`** with:

```kotlin
SQLiteConfig().apply {
    setPragma(Pragma.CIPHER, "sqlcipher")
    setPragma(Pragma.KEY, base64(secretStore.getOrCreateKey("database")))
    setPragma(Pragma.JOURNAL_MODE, "WAL")
    // …
}
DriverManager.getConnection("jdbc:sqlite:<path>", config.toProperties())
```

The driver bundles **SQLite3 Multiple Ciphers**, which implements SQLCipher-compatible cipher schemes
(`PRAGMA cipher`, `PRAGMA key`). It is not Zetetic's Android SQLCipher binary, but it is the same
SQLCipher-compatible database format/mode for a new desktop database (G6 allows a different local format
provided wrong-key/WAL/migrations are proven — they are). The 32-byte random secret is passed as a
Base64 **passphrase**, so SQLCipher's PBKDF2 derives the working key; it is not the raw-key pragma.

  `LICENSE.zentus` BSD-3-Clause for the original Xerial/David Crawshaw code; `Bundle-License` in the
  manifest is Apache-2.0).
- Bundled **SQLite3 Multiple Ciphers** — **MIT** (Ulrich Telle, upstream
  <https://utelle.github.io/SQLite3MultipleCiphers/>).

## 9. Linking still needed (WP05 part B, not implemented)

The desktop is currently a **local-only identity**; it acts as `primary` on its own mailbox because it
never shares the phone's identity. To finish WP06's linking:

1. Generate an ephemeral X25519 key pair and 16-byte link code; render
   `RELAYLINK:1|E:<eph pub>|C:<code>|N:<computer name>` as a QR/link screen.
2. Consume the WP05 server link slot (`PUT/GET /v1/link/<sha256(code)>`, proof header, TTL, single-read
   or retrieval lease — G1 says not to delete on the first network read), and the phone-side
   `POST /v1/devices` enrollment.
3. Open the HPKE-sealed link bundle and import the Nostr secret, Tink current/previous keysets,
   contacts, group rosters, profile/settings and the new `deviceId`; persist them through the existing
   `SecretStore`/`DesktopKeyMaterial`/`DesktopIdentity` seams.
4. Persist the `deviceId` and pass `device=<32hex>` on `GET /v1/inbox`, `POST /v1/ack`, `GET /v1/ws`,
   media calls, and start the cursor at the server's head (the current transport sends no `device`
   parameter and therefore behaves as `primary`).
5. Implement the G1 device-authorization contract (phone-only admin key, per-device keys, revocation on
   HTTP/WS/media) and the link-slot rate limits; the current shared-key `device=` is bookkeeping, not
   authentication.
6. Add the link screen UI/state and the unlink/revocation flow.

Until then, the UI label and this evidence deliberately say “phone linking is WP05 part B”.
