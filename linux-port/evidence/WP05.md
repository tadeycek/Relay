## What part A closes

Gate G1 in `linux-port/10-readiness-gates.md`: `device=primary` is no longer authority. An identity may migrate to a
**phone-only administration key**; after migration only that key may enroll or revoke devices. Each linked device
gets its own authentication key bound to the shared mailbox identity. Every HTTP and WebSocket surface resolves the
signer to an `(identity, device)` pair and refuses revoked, unknown or wrong-device keys. Legacy identities that
never migrate keep the WP04/shared-key behaviour byte-for-byte.

2. **No UI or `MailboxTransport` wiring.** The app plumbing is behind the existing `MailboxAuth.header(signer, …)`

3. **No SFU route exists yet.** `src/index.ts` has no `/v1/call/...` surface, so "SFU proxy" enforcement is the same
   `authorize()`/`resolveSigner()` gate used by every other route; when WP11/WP15 add the proxy it must call that
   gate. No call code was invented here.
4. **Migration key.** WP04 kept `meta.schema = 7` and tracked device tables under `devices_schema`. The new columns

5. **The admin key's identity is the target identity.** A device-management request signed by an admin key acts on
   the mailbox that key is bound to. A key belonging to another identity cannot target this identity; it is refused
   by membership (`403 not_allowed`). This is the protocol's only interpretation without a separate target-identity
   field. The "another identity's admin" test was corrected to a rogue non-member key because the original assumed a
   target identity the protocol does not carry.

## Security review defects and fixes

The first implementation passed its own suite but was blocked by an independent review. Each defect was reproduced
with a failing test first (`device-auth-hardening.test.ts`; 11 RED before the fix), then fixed.

| # | Defect | Fix | Regression test |
|---|---|---|---|
| **B1** | Migration never closed or rebound sockets authenticated with the shared identity key; `sync`/`ack`/`signal`/push only checked expiry and membership, so a pre-migration socket kept advancing the primary cursor and deleting messages for up to the 1 h TTL. | `Session` now stores the signing key. On a successful migration every socket tagged with the identity is closed `4001 auth_invalid`, and `session()`/`bindingFailure()` re-checks the signer on every frame and push: shared key of a migrated identity, rotated key, mismatched device or revoked device is refused. | "closes an open shared-key socket…", "refuses sync/ack/signal/push on a shared-key socket whose close sweep was missed" (state injected in-memory), "keeps an enrolled device socket working". |
| **H2** | `devices.auth_pubkey` had no UNIQUE constraint, enrollment did not check reuse, and `resolveSigner` took an unordered `[0]`, making attribution arbitrary. | `devices_schema` v3: duplicates are backfilled deterministically (lexicographically first `(pubkey, device)` keeps the key; others are blanked, preserving cursors), then a partial UNIQUE index is created. `enrollDevice` refuses a key owned by another pair/identity with `409 auth_key_in_use`; `resolveSigner` orders deterministically and stays revoked-aware. | "refuses enrolling one key for a second device id", "refuses a key already used by another identity's device", "keeps a UNIQUE index…", "backfills duplicate keys deterministically". |
| **H3** | An admin key equal to a device key was accepted; `adminByKey` was consulted first, so two tables could claim one key. | **M4** | Key rotation updated `auth_pubkey` without closing the old key's socket. | Rotation is still allowed (documented as not revocation; `DELETE` is), but the rotated device's sockets are closed `4001 auth_invalid`; the old key no longer resolves. | "closes the device's socket when its key is rotated, and the old key stops working". |
| **M5** | `handleSend` had no in-transaction recheck, so a send authorized just before a DELETE could still store. | The write section is `sendStored()`; it re-reads `revoked_at` and the migrated/shared-key state in the same synchronous section as the inserts and returns `401 auth_revoked` before storing. | "refuses a send whose device was revoked between authorization and storage" (authorizes, revokes via SQL, then calls the write section). |

## Exact revocation semantics implemented

1. `DELETE /v1/devices/<id>?device=primary` signed by the admin key sets `revoked_at = now` and refreshes
   `last_seen`, inside one `transactionSync`. It removes the device's cursor from the deletion floor immediately
   (`revoked_at = 0` filter), so messages only that device held are freed at once.
2. The server closes every socket tagged `deviceTag(identity, id)` with code `4009` reason `unlinked`.
3. Every later request signed by that device's `auth_pubkey` is resolved by `resolveSigner()`, which returns
   `revoked: true`; `authorize()` returns `401 auth_revoked` before any route logic runs. This covers `send`,
   `inbox`, `ack`, `ws`, `invite`, `pair`, `push-token`, `/v1/devices`, and media PUT/GET/DELETE. Any SFU proxy
   added later must use the same gate.
4. Re-enrolling the same device id with a new key (admin only) clears `revoked_at`, sets the cursor to the current
   head and gives it a gap watermark. The old key stays unusable. Rotating the key of an **active** device keeps
   its cursor but closes its sockets with `4001`; it is a key change, not a revocation.
5. Revocation does **not** erase the Nostr or Tink secrets on the computer, cannot stop direct contact-to-contact
   sends, and cannot stop decryption of already-downloaded data. Full revocation needs a new identity and re-pairing.

## Limitations

- **Server-side access revocation only.** The revoked computer still holds the shared Nostr/Tink secrets it learned.
  It cannot use this server, but it can decrypt what it already has and can send to contacts directly. This is the
  honest G1 limit; no protocol can take back a key already copied.
- **Migration does not erase the shared identity secret.** It closes the identity's sockets immediately and refuses
  the shared key afterwards, but a phone or computer that already held the identity key still has it. It can no
  longer use this server under that key and cannot open newly stored messages, yet the key itself is not revoked.
  Only a new identity and re-pairing removes that exposure.
- **Session semantics after the fixes.** Migration closes the identity's sockets at once (`4001`); rotation closes
  only the rotated device's socket (`4001`); DELETE closes `4009`. Remaining sockets still expire at the 1-hour
  session TTL, and every frame/push re-resolves the signer, so the sweep is a fast path and not the only barrier.
  A socket that survives a failed close can send frames but every one is refused before it pages, acks, relays or
  receives.
- **Admin key custody.** The admin key is the authority. The app stores it in Keystore-backed encrypted preferences;
  anyone who extracts it can enroll or revoke devices. It must not be exported in the link bundle (part B).
- **One admin key per identity.** The schema stores one row per identity. Rotating the admin key is not implemented;
  it would require a migration/re-key endpoint. A lost admin key means replacing the identity.
- **No target-identity field.** Device management acts on the admin key's own identity. A key belonging to another
  identity cannot target this identity; the protocol has no field to name a target, and the server does not accept a
  device's claim to be primary as authority. This is a deliberate simplification, not a hidden capability.
- **Rate limit is in memory.** `MAX_ADMIN_OPS_PER_MINUTE = 10` resets on object eviction. Replay is persisted and is
  the real guard; the rate limit is best-effort against a hot key.
- **Media and the SFU proxy** use the same `authorize()` gate. Media is tested; no SFU proxy exists in this tree, so
  its enforcement is NOT RUN until WP11/WP15 add the route.
- **Phone-side network/Keystore glue is untested in this environment** (Android `Context`/Keystore, no Robolectric in
  the app test module). The lost-reply decision rule is unit-tested; the HTTP calls and preference writes around it
  compile and are exercised only indirectly.
- **Enrollment binding and replay across requests.** The NIP-98 event covers method, exact URL (including query),
  body digest, timestamp and nonce. A captured enrollment cannot be replayed; a captured request cannot be edited.
- **No deploy or 48 h pilot.** WP04-AC6 and any WP05 deploy/pilot remain NOT RUN.

## Smallest next step for part B

Part B starts with the **link slot**: `PUT /v1/link/<sha256 hex>` (NIP-98, primary/admin key, ≤128 KiB sealed
bundle, 10-minute TTL, one slot per member) and the unauthenticated `GET` with a proof header (not a query
parameter), single-read with a short retrieval lease and explicit completion so a lost response does not consume
the bundle. Then `:core` `LinkBundle` HPKE seal/open and the first `SYNC|KEYS`/`SYNC|SENT` codecs. The device
authorization contract above is the prerequisite and is now in place.
