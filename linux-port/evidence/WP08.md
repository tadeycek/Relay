## What it does
- **Send**: picker (`FileDialog` filtered to jpg/png/gif/webp/mp4) and drag-drop; routed by magic number, not extension. `prepare` validates (symlink-free path, regular file, ≤100 MiB source, magic number, header dimensions), applies the phone's rules (JPEG/PNG >900 KiB or >1280 px or EXIF-rotated → bounded sub-sampled decode, orient, JPEG ≤900 KiB; GIF/WebP/MP4 as-is), caps plaintext at `MAX_STORED_BYTES-28` (blob ≤ 25 MiB), encrypts once with `MediaCrypto`, writes the raw `iv||ct||tag` blob 0600 in a 0700 folder, and commits the journal row + visible bubble in one transaction before any network call. Upload recipients are `[contact, own identity]`; `transport.sendWithMedia` carries the blob digest in the signed `media` list; the SENT copy (sealed to self) goes through `queueMediaSync` with the same digest; the sender confirms only after the SENT copy was published.
- **Receive**: `TYPE:MEDIA` is accepted only for direct chats and within the 7-day window, stored durably (journal row exists before the mailbox may ack), then `downloadTo` a private partial file with the shared client (bounded, digest-checked, per-device `?device=` signature), ciphertext SHA re-verified, `MediaContainer.unwrap ?: raw`, `MediaCrypto.decrypt`, authenticated plaintext size must equal `SIZE`, then classified. Only after the blob is atomically renamed and fsynced does the device `confirm`. Hostile URL origin, size above the client bound, and groups never reach the network.
- **Safe rendering**: `MediaSafety.verdictForIncoming` is header-only. IMAGE only when magic number == declared MIME and dimensions ≤8192 per side and ≤16 MP; then Skia decodes the verified bytes (first frame only, so a GIF never animates) in the bubble. Magic/MIME confusion, bad header, over-bound dimensions, unknown format → `ATTACHMENT` (save only). MP4 → `VIDEO`: never parsed or decoded in process; placeholder + explicit "Open externally…" (confirmation dialog, then a verified 0600 export inside the media folder handed to `java.awt.Desktop.open`) and "Save as…". `previewBytes` re-verifies the verdict, so a hostile journal row cannot force a decode.
- **Progress / retry / cancel / delete / retention**: progress from bytes written/uploaded; Retry (non-permanent failures), Cancel (persistent tombstone fenced against every state update and active I/O), Delete (wipes key from record and bubble, removes ciphertext and exports), 7-day retention purge, startup sweep (orphans, partials, exports, `.stage-*`), private quota, no-overwrite/no-symlink save-as. Honest states: offline → retryable FAILED "Network problem…"; 404 → permanent "no longer available"; 401/403 → permanent "server refused this device"; integrity → permanent "Integrity check failed"; no mailbox → `OfflineMediaTransport` (stored media still opens).
- **Sending is default OFF** like WP09 files: `enableMediaSend` / `--enable-media-send-for-tests`; receiving is always on. The composer button explains when sending is off.

## AC4/AC3 decision — video (AC3)
**Decision: no in-process video player in WP08.** MP4 is attacker-controlled input to a large native parser; an in-process player (e.g. a bundled VLC/FFmpeg/GStreamer binding) would add a multi-tens-of-MB native dependency with LGPL/GPL obligations and a decoder in the trust boundary of the process holding the identity keys. Instead: placeholder (no poster extraction), explicit open of a verified private export in the user's system player, explicit save. Licence of the chosen component: none added — the hand-off uses `java.awt.Desktop` from the bundled OpenJDK (GPLv2 + Classpath Exception, already shipped) and the user's own installed player; images use Skia/Skiko already bundled (Apache-2.0). Trade-off accepted: no inline playback and no poster frame; the external player parses the video outside Relay's sandbox. Recorded as [LP-D18](../03-decisions.md).

## Review-fix round (B1–B4)
- B1 pending own-device grant: 404 after SENT publication retries with a 1 s throttle inside a 60 s window, then is a permanent "no longer available"; no sleep, never confirms missing bytes.
- B2 every confirm attempt re-opens the blob (SHA-256, AEAD, size, verdict); tamper while CONFIRM_PENDING is a permanent integrity failure, no confirm.
- B3 `/v1/send` 200 with a non attached/pending media status fails closed (non-retryable). `POST /v1/sync` replies are judged by `SyncWire.checkMediaReply`; a `gone`/missing grant is a `final` rejection (no same-id retry), and the media row becomes a permanent failure without confirming. This touched `DesktopSyncHttp.kt` (parse hook) outside the owned list.
- B4 `confirmOutcome`: 401/403 = refused (permanent, "server refused this device"), 429/5xx = retry.
- RED evidence: B3-sync tests failed first (4); B1 throttle/window test was added after the code and is RED by mutation check only (not a first-run failure).
