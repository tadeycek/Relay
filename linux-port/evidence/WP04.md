### Projection for 10 users / 3 desktops — an ESTIMATE from the measured per-op rows

Assumptions (all mine; change any and the result moves): baseline = the README's **27,000 rows/day** for
10 users × 100 messages, 30 % groups, including the probe (the README figure, not re-measured here), which implies
about 3,700 deliveries/day at 7.3 rows per delivery+confirm; the 3 desktops are on 3 different users, who receive
3/10 of deliveries (≈1,110/day); each delivery to them is acked separately by both devices (no batching);

## Limitations and where behaviour differs

G1 / security (state plainly, do not oversell):
1. **`device=primary` is not proof of being the phone.** Any holder of the Nostr secret can send any `device`.
   A linked desktop can register/remove devices, ack for the phone (deleting messages the phone has not stored),
   and read as any device.
2. **An unlinked device can still read with the shared identity key.** `DELETE /v1/devices/<id>` removes a
   cursor and closes sockets with `4009`; it does not revoke the key. The unlinked computer can reconnect without a
   `device` parameter (or with `device=primary`), call inbox/ack/ws, receive live pushes, and fetch media for which
   `primary` is a recipient. It also keeps the Nostr and Tink secrets it already learned. Real revocation needs
   per-device keys (WP05) or a new identity (LP-D02 consequence, 09 R3).
3. Revocation checks on media (`unknown_device` for an unlinked id) are equally bypassable with `device=primary`.

Behaviour that differs from legacy:
4. For an identity that **has** linked devices, a legacy client acting as `primary` finds messages and media held
   until the other active devices ack/confirm, or up to 72 h after they go silent, and each of its acks costs more
   rows (5 vs 3). Its replies remain byte-identical. For an identity with no devices nothing differs.
5. New error codes `unknown_device` (403), `not_primary` (403), `device_limit` (409); a legacy client that sends a
   non-primary `device` gets 403 where it used to get its request processed (the parameter was previously ignored on
   ack/ws/media and rejected with `400` on inbox).
6. `/v1/inbox` now accepts `device` (it still rejects any other unknown parameter).

Design limits:
7. Dormancy is evaluated when a request/ack arrives, never by timer; with no acks nothing is freed. Accuracy ≈ 1 h
   (hourly `last_seen`).
8. Messages deleted for a dormant device are gone; `gap` says something is missing, not what.
9. `head` and a new device's start are global seq values. A new device that asks with `after < head` can still read
   pre-link pending ciphertext; the client must start from `head` (LP-D06 is client discipline here).
10. **Upload → enrol → send race.** The media recipient snapshot is taken at PUT. A device registered after the PUT
    but before the sender's message is sent will receive the message and get `404` on the blob. Mitigation not
    implemented: the sender re-PUTs the same blob (idempotent, adds pairs) immediately before sending, or the server
    admits late devices on GET. Test coverage asserts the snapshot semantics only.
11. A media device is waived at the next confirm or at the early alarm (`last_seen + 72 h`, accurate to the hourly
    refresh); a waived pair's row is dropped, so that device later gets `404`.
12. Once an identity has any `devices` row it stays on the linked code path even after every desktop is removed
    (acks cost 5 rows instead of 3). No cleanup job exists.
13. Cursor/device rows for an identity are never purged. `cursor_state.high` is written but only used as audit data.
14. `ackDevice` clamps `through` to the global head; the legacy path does not (the observable result is the same
    because no row exists above the head).
15. Socket 4009 for an unlinked device works while the object is awake; the sockets are found via the hibernation
    API tag, which survives eviction (not separately tested).
16. Rows for `x-relay-sql-rows` on the media object cover that object only; RPC rows are on the Mailbox object.

## Risky spots for review

- `Mailbox.enter()` — the single place where dormancy is evaluated, `last_seen` refreshed and the gap watermark
  written; ordering is load-bearing (mutation-tested). Runs inside `transactionSync`.
- `deleteBelowMin()` writes `cursor_state.floor` **before** deleting rows; the `ON CONFLICT … WHERE excluded.floor >
  floor` keeps the floor monotonic. `prune()` also raises it on expiry.
- `registerDevice()` uses the global `sqlite_sequence` head as the new device's cursor and, on first call,
  derives the primary's position from `MIN(seq)-1` of its pending rows. Verify with a real pre-existing queue.
- `MediaBlob.settle()` awaits an RPC between reads and writes; it re-reads after the await. `forget()` →
  `deleteAll()` + `migrate()` re-creates the v2 layout.
- `MediaBlob.alarm()` keeps the original "erase" behaviour unless a linked device is still waiting and the lifetime has
  not elapsed.
- The separate `devices_schema` meta key (scope decision 2).
- `DEVICE_ROUTE` in `index.ts` lets `/v1/devices/primary` through so the object can answer `400`.

## Third-context reviewer fixes (2026-10-23)

- **Alarm invariant:** a blob with any unconfirmed pair always re-arms at the earlier of its lifetime and the next linked-device dormancy. The new A-primary + desktop / B-primary test failed RED (`alarm: null` after A's desktop was waived), then passed GREEN, including the forced >8-day lifetime erase.
- **Expiry gap:** `prune()` persists a gap for each device whose cursor is below the new expiry floor, even if it is currently active. The new active-device test failed RED (`gap` absent), then passed GREEN; ack-before-show does not clear it, show + later ack does.
- **Same-media-object concurrency:** `fetch` and `alarm` now wrap the complete async lifecycle in `ctx.blockConcurrencyWhile`, including mailbox RPC and the two awaits in `forget()`. Concurrent repeat-PUT/confirm and dormancy-settle tests pass, but they also passed before the guard and are **not deterministic barrier proofs**. A test attempting a barrier via a promise outside `runInDurableObject` crashed workerd; a direct invocation inside it bypassed runtime event serialization and returned 503. Neither was counted as valid RED evidence. Reactivation of a device in the separate Mailbox object during an already-returned device-state RPC is not transactionally coupled to the MediaBlob and remains unproven under this test setup. Do not promote this race to a fully demonstrated AC.
- **Upload→enrol→send:** remains open. The send payload has only opaque encrypted envelopes (`to`, `id`, `envelope`); it does not carry a trustworthy attachment hash. No server-only arbitrary-blob update was made. AC4 is **BLOCKED** pending a contract/client change or approved sender-side re-PUT protocol.
- **G1:** primary-device spoofing with the shared Nostr secret remains the WP05 security gate; no per-device authentication was added.
