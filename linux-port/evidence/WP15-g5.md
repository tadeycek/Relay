## Residual blockers

1. **No signed roster.** The member list is claimed by the creator. Any server member who knows a group UUID can squat a (group, revision) slot with a self-chosen set (denying the real group's call until it ends or the 12-minute unjoined TTL) or supersede with a higher revision that lists themselves. Closing this needs a signed owner roster revision that the server verifies (WP02/WP16 contract).
2. **Creator-only removal/rotation.** A group owner who did not start the call cannot revoke through the server; the creator's client must send `roster`, or the owner ends the room via the creator.
3. **`rosterHash` is stored, not verified.** The server has no owner/algorithm input; clients must compare the `rosterHash`/`revision` from `GET /v1/call/rooms/<room>` with their own `GroupCallCodec.rosterHash`.
4. Superseding or ending an older room is best effort (a failed RPC leaves it to its own alarms); slot table is capped at 256 groups and unreleased slots are trusted for 24 h.
5. Provider session close on removal (see NOT RUN), live-state/stale-banner query on clients, fan-out authentication (`VerifiedGroupSender`), and WP17 key epochs/rotation remain with the client WPs.

## What core/app/desktop must send

All requests are NIP-98 signed with the acting device (`?device=<id>` as today). Bodies carry `"v":1`.

1. **Create** (starter): `POST /v1/call/rooms` `{v:1, room, secretHash, group:<UUID from GroupProtocol.State.id>, revision:<Long>, rosterHash:<GroupCallCodec.rosterHash(roster)>, members:[owner and members' identity pubkeys, 64 lowercase hex, sorted ascending, unique, max 64]}`. The starter must be in `members`. Answers: `200 {created:true,rostered:true}`; `409 group_room_exists` with top-level `room` (join that room using the secret from the winner's `group_start`, discard the own room id and secret and do not send a `group_start`); `409 stale_revision` (refresh the roster); `403 not_in_roster`; `400 roster_required`/`bad_request`. Never fall back to a legacy create after an error. Send `group_start` only after a 200.
2. **Join**: as today (`GET …/ws?secret=…&pid=…`); new refusal `403 not_in_roster` means the identity is not in the frozen set. Treat a `404` from `GET …/rooms/<room>` and close code **4009** (`removed`/`auth_revoked`) as "access revoked, do not auto-reconnect". Handle the new `end` frame field `reason:"superseded"`.
3. **Live state / banner**: `GET /v1/call/rooms/<room>` returns `rostered`, `revision`, `rosterHash` for bound rooms; compare with the local roster before trusting the room; 404 clears the banner (also for removed members).
4. **Removal** (creator's client, after a roster update removes members): `POST /v1/call/rooms/<room>/roster` `{v:1, remove:[pubkeys sorted unique, none the creator, all currently in the set], secretHash?:<sha256 hex of a fresh 64-hex secret>}`; then re-distribute the new secret E2E to the remaining members. Additions or a creator removal need a new revision (new room) or `POST …/end`.
5. **Rotation**: `POST /v1/call/rooms/<room>/rotate` `{v:1, secretHash}` (creator only); distribute the new secret E2E; open sockets keep working.
6. Hosts own: fence/replay persistence, `VerifiedGroupSender` only after a verified seal, and the `confirmedRoom` signal only after an authenticated join plus a successful live-state readback of exactly that room.

## Canonical bytes and verification

```
relay-call-roster-attestation-v1
v=1
groupId=<uuid>
revision=<decimal>
rosterHash=<64 hex>
members=<sorted 64-hex, comma separated>
room=<32 hex>
issuedAt=<decimal seconds>
expiresAt=<decimal seconds>
```

Signature = BIP-340 over `SHA-256(UTF-8(that string))`. The Worker checks shape, recomputes
`rosterHash = sha256("relay-group-call-roster-v1\n" + group + "\n" + owner + "\n" + revision + "\n" + sorted members
joined by "\n")` and requires equality with the body, checks the window, then verifies the signature
(`@noble/curves` schnorr). Failures are `400 roster_unverified` (nothing stored). A different owner for a group
already pinned is `403 not_owner` before any slot claim.

## Supersede rules

- Verified signed higher revision: replaces the slot regardless of the old room's roster.
- Unsigned higher revision: allowed only when the old room is **not** verified and its frozen roster contains the
  creator; against a verified room it is `409 signed_roster_required` (dead peer counts as verified: fail closed).
- Same (group, revision) conflict is unchanged (`409 group_room_exists`), signed or not.

## What Android and desktop must send

1. Build the attestation from the local `GroupProtocol.State`: `groupId = state.id`, `revision = state.revision`,
   `owner = state.owner`, `members = state.members.map { it.key }.sorted()` (strictly ascending, ≤64), `room` = the
   room id in the `group_start`, `rosterHash = GroupCallCodec.rosterHash(state)`, `issuedAt = now seconds`,
   `expiresAt = now + 600` (≤900).
2. Sign `SHA-256(RosterAttestations.canonicalBytes(template))` with the owner's existing Nostr key via
   `RosterAttestationSigner`. Core provides the seam only; Android implements it over its rust-nostr `Keys`
   (`signSchnorr(hash)`), desktop over its secret store. Only the group owner's device should sign — the other
   members send the same verified fields they received in the E2E `group_start` (they cannot mint them).
3. `POST /v1/call/rooms` adds `"owner"`, `"rosterSig"`, `"issuedAt"`, `"expiresAt"` to the existing roster body.
   Treat `400 roster_unverified` / `403 not_owner` as fatal: do not retry unsigned, do not silently downgrade.
   `409 signed_roster_required` means "refresh the roster and send a signed revision".
4. Read `verified` from the create answer and from `GET /v1/call/rooms/<room>`; only show the roster as

5. `verified:false` (legacy) must not be presented as owner-verified. `ALLOW_UNROSTERED_CALLS="0"` remains a release

## Residual risks (documented, not fixed)

1. **A compromised or malicious owner key still wins.** The signature proves the owner key signed this roster, not
   that the roster is the group's real membership. This is the honest ceiling of the design.
2. **Owner pinning is trust-on-first-use.** The first verified owner key per group is pinned in the Mailbox. A member
   who gets a self-signed roster in first (for a group the server has never verified) pins themselves; the real owner
   then gets `403 not_owner`. There is no group directory to check against. `403 not_owner` is also an oracle for
   "this group already has a pinned owner".
3. **Legacy path remains.** An unsigned create can still claim an unclaimed `(group, revision)` slot (12 min TTL) and
   can hold the same revision so a signed create gets `409 group_room_exists`. It can no longer supersede a verified
   room. Turn `ALLOW_UNROSTERED_CALLS` off to remove it.
4. **No owner-key rotation/revocation.** `/roster` removes members from the live set; the pinned owner key and the
   frozen `rosterHash` do not change. Changing the owner is out of contract.
5. **Clock dependence.** A skewed owner clock beyond ±300 s fails the create; the error is `400 roster_unverified`,
   which a client cannot distinguish from a bad signature (deliberate: no oracle on why it failed).
6. **Metadata.** The Worker sees the owner pubkey during verification (not stored) and the Mailbox stores
   `sha256(group) → owner`. Roster membership was already visible for bound rooms.
7. **Not constant-time.** The core verifier uses plain `BigInteger` affine arithmetic over public data only
   (signature + pubkey). Do not reuse it for secret-dependent work.
