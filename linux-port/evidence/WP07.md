## 1. What this pass changed in `desktop/**`

New desktop sources:

- `DesktopChat.kt` — the window's state machine. Rebuilds `ChatUiState` from the encrypted store on every
  engine revision, restores the selected conversation from `meta("ui.selected")`, persists drafts, marks
  conversations read, and routes send and own-profile actions to the engine seams. Store work runs on
  `Dispatchers.IO` behind a `ChatReads` seam with profiles preloaded once per refresh; state is published from
  the UI scope and only the newest refresh generation may publish. Draft writes are debounced and fenced per
  conversation, so a pending write cannot resurrect text after a successful send, and a failed send puts the
  draft back immediately (`ChatUiState.draftVersion`).
- `DesktopChatUi.kt` — the Compose three-pane UI: guild rail, conversation list (1:1s and groups mixed,
  avatars/initials, unread badge, last-sender preview, timestamp), thread (sender grouping, timestamps,
  honest unsupported-message label), composer (Enter sends, Shift+Enter inserts a newline at the caret,
  offline/error banners), **read-only** members panel with an "Edit groups on your phone" note (LP-D03: no
  create/rename/add/remove/avatar controls on desktop; the group composer stays enabled), settings dialog with
  name/avatar and an about/licences line, Ctrl+K quick switcher.
- `DesktopUi.kt` — pure presentation model: `RailItem`, `ThreadRow`, `MemberRow`, `ChatUiState`, rail sorting,
  five-minute sender grouping, clock labels, and the "Unsupported message — update Relay to read this" label.
- `DesktopGroups.kt` (protocol/store layer, not edited in this pass; no desktop UI path calls the editors) — group create, rename, add/remove member, owner-only avatar, direct v2 fan-out to every
  member over the existing seal+send path, held-event replay, and rejection of non-owner rosters.
- `DesktopProfiles.kt` — own/peer display name and avatar publication and receive with revision guards.

Changed desktop sources:

- `DesktopMessageStore.kt` — schema v3 adds `group_rosters`, `profiles`, `conversation_state` and `group_pending`
  (additive migration), plus roster/avatar/profile/read/draft/held-event queries and `lastMessage`.
- `DesktopEngine.kt` — constructs the group/profile seams on the existing `Transport`, routes group
  conversation sends through them, intercepts group/profile control bodies in the receive path, and fans
  group avatar requests out to the owner.
- `Main.kt` — `App` now renders `ChatScreen` through the `DesktopChat` controller; drag-and-drop, the link
  screen, `RelayTheme` and the `main` entry point are unchanged. A diagnostics-only `--show-chat-ui` flag
  bypasses the link gate so the UI can be captured without a phone; it now **fails closed**: without both an
  explicit non-blank `--config-dir` and `--data-dir` it prints a message and exits 2 (verified on the packaged
  app: `failclosed exit=2`), so it can never open the user's real profile.
- `desktop/build.gradle.kts` — `compose.desktop.uiTestJUnit4` test dependency for WP07-AC3.

New/changed desktop tests in this pass: `DesktopChatUiTest` (11, Compose semantics tree incl. real Enter /
Shift+Enter key events, editor controls absent, failed-send restore), `DesktopChatControllerTest` (8, real
controller + real encrypted store + stub transport: failed send restores draft, debounce fence, bounded profile
lookups off the UI thread, stale-generation drop, raw `TYPE:HOLOGRAM` and missing-avatar rows through the
store -> controller -> `ChatScreen` path, no roster-edit API), `DesktopUiStateTest` (13, incl. `--show-chat-ui`
fail-closed parse). No existing test was deleted or weakened.

### 2.1 Group traffic over the real local Worker

```sh
RELAY_GROUPS_E2E=1 ./gradlew --no-daemon --console=plain -Dorg.gradle.java.home=$JAVA_HOME \
  -Dorg.gradle.jvmargs=-Xmx3g :desktop:test --tests '*DesktopGroupsWorkerTest' --rerun-tasks
```

**BUILD SUCCESSFUL in 33s**, 1 test, 0 failures/errors. The test printed:

```
WP07_GROUP_WORKER_OK desktop=5430…9039 alice=e705…a759 bob=b2b8…e727 members=3
peer_post_stored=true desktop_post_sent=2 rename_rev=2 avatar_rev=0 port=8799
```

It starts a local `wrangler dev` Worker on port 8799 with all three pubkeys allowlisted, builds the desktop
and two independent JVM peers on the production `DesktopMailboxTransport`, creates a 3-member group from the
desktop, receives the roster on both peers, has Alice post **directly to the other members** (desktop stores
it once with sender Alice and one unread), sends a desktop post that both peers decrypt and read as authored
by the desktop, renames the group to revision 2 and delivers an owner-authenticated avatar to both peers. It
also feeds the desktop a forged non-owner roster and asserts the local roster does not change.

## 6. Known limits and gaps

1. **AC2 seam gap (blocked, not worked around).** `core/.../SyncCodec.kt` defines `SyncBody.Group` and the
   desktop's mailbox transport delivers sync bodies, but nothing in `app/` stages a group roster into that
   body. Implementing the desktop half alone would define a wire schema from one side; that is a core/phone
   contract decision for WP05, so it is reported here rather than guessed. No `core/**` file was changed.
2. **AC1 topology.** The JVM-peer Worker test proves the direct-delivery and persistence path but not real
   phone key material or emulator push behaviour.
3. **Notification actions.** The "desktop notification actions (open conversation)" step from the WP has no
   implementation and no seam in this tree.
4. **Diagnostics flag.** `--show-chat-ui` renders the chat UI without a linked phone and now requires explicit
   `--config-dir` and `--data-dir` (fail closed, exit 2). It does not change crypto, storage or transport.
5. **Held events** are bounded to 100 per group / 500 total / 7 days, matching the phone's `SharedGroups`.
6. **Group files** remain disabled (`DesktopFiles` rejects group conversations), unchanged from WP09.
