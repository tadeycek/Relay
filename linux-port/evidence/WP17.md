## Frozen format implemented

From `evidence/WP02-e2ee-interop.md` and `spikes/calls/E2EE-INTEROP-EVIDENCE.md`:

```
frame = hdr[1] (first Opus byte, clear, GCM AAD)
      | AES-128-GCM(ciphertext || 16-byte tag)
      | IV[12] | ivLen[1] = 12 | keyIndex[1]
overhead = +30 bytes;  keyIndex = epoch (0..255)
```

Zero-length frames are rejected (`TOO_SHORT`) and never re-emitted: they carry no audio, and both Android
`FrameCryptor` and the WP02 notes pass the 3 stream-start zero-length frames in clear. A host that forwards
them instead of dropping them would leak nothing but would break the "no mixed plaintext" invariant, so the
desktop transform must `drop()` them.

## Key schedule (deterministic on both platforms)

`GroupCallKeySchedule` version 1, 32-byte E2E call key, epoch = keyIndex:

```
HKDF_SALT   = SHA-256("relay-call-frame-v1/extract")
ratchetSalt = HKDF-SHA256(callKey, HKDF_SALT,
                 "relay-call-frame|v=1|epoch=<n>|purpose=ratchet-salt", 32)
materialRaw = HKDF-SHA256(callKey, HKDF_SALT,
                 "relay-call-frame|v=1|epoch=<n>|sender=<64-hex pubkey>|device=<device>|purpose=frame-material", 32)
material    = lowercase hex ASCII of materialRaw          (64 bytes)
aesKey      = PBKDF2-HMAC-SHA256(material, ratchetSalt, 100000, 128)   (16-byte AES-128)
```

The ASCII-hex step is deliberate: JCA `PBKDF2WithHmacSHA256` takes a `char[]` and UTF-8-encodes it, while
Android's native PBKDF2 hashes raw password bytes. 64 ASCII hex characters hash identically on both sides.
The exact test vector (call key `00..1f`, participant `a*64`/`phone`):

```
HKDF salt    75fe2452eaecb31bc42856a63a62a76af1aa0f15199a80af15ca12a7b6d2a58f
ratchetSalt  86b151c8a8815b0205d5f0648fc45c1ba47946bb85af3ddfc9647d69bf3e6ca8
material     39b2dafb181089a8991e2b0c56fdd038b5068e368bddb62bb1d52c0833c1cfdb
aesKey       46dfb90239209d6ec81a7739d8e6436d
```

The vector was generated independently with Python `hashlib`/`hmac` (not with this Kotlin code) and pinned in
`GroupCallKeyScheduleTest.fixedInteropVector`. Rotation to epoch 1 with call key `20..3f`, remaining
`b*64`/`desktop`: ratchet `6a1be5a6…9627`, AES key `db9aae0439bf962c6b3958ec803c1088`, also pinned.

Rotation: `rotateForRemoval(remaining, freshCallKey)` requires a different 32-byte call key (reusing it is
rejected because the removed member knows it), a strict subset of the current devices, epoch < 255, and marks
the old epoch retired. `GroupCallEpochKeys.classify` returns `RETIRED` / `UNKNOWN_KEY_INDEX` /
`UNKNOWN_SENDER`; `open` returns `RETIRED_KEY_INDEX` etc. and never decrypts with a non-current epoch.

## Replay

`GroupCallReplayGuard` uses a 256-bit sliding window per (sender device, epoch, SSRC). RTP sequence numbers
are 16-bit and are extended per SSRC by `RtpSequenceExtender` (wrap +65536, late pre-wrap −65536). The
encoded frame has no counter, so the host supplies `getSequenceNumber()` and `getSsrc()`. **Admission happens
after `open()` returned `Opened`**, otherwise a forged high counter could advance the window and drop real
frames. A full stream table returns `STREAM_LIMIT` rather than evicting an active window.

## Host integration required (not applied)

### Android — `GroupSfuPeer` and `GroupCallController`

`FrameCryptorKeyProvider` takes the ratchet salt once at creation, so create one provider per epoch and
rebuild/dispose the cryptors on rotation. `setKey` must receive `materialFor(p)` (ASCII, 64 bytes), not the
raw HKDF digest and not the AES key.

```kotlin
val schedule = GroupCallKeySchedule.fromCallKeyHex(e2eeKeyHex, participantDevices)
val provider = FrameCryptorFactory.createFrameCryptorKeyProvider(
    /* shared = */ false,
    /* ratchetSalt = */ schedule.ratchetSaltCopy(),
    /* ratchetWindow = */ 0,
    /* uncryptedMagicBytes = */ null,
    /* failureTolerance = */ 0,
    /* keyRingSize = */ 1,
    /* discardWhenNotReady = */ true,
    /* algorithm = */ FrameCryptorKeyProvider.FrameCryptorKeyDerivationAlgorithm.PBKDF2)
schedule.participants.forEach { p ->
    provider.setKey(p.frameCryptorParticipantId(), schedule.keyIndex, schedule.materialFor(p))
}
```

Sender (in `GroupSfuPeer.prepareMicOffer`, replace the ignored `pc.addTrack(...)` result):

```kotlin
val rtpSender = pc.addTrack(track, listOf("relay-group"))
val cryptor = FrameCryptorFactory.createFrameCryptorForRtpSender(
    factory, rtpSender, me.frameCryptorParticipantId(), AES_GCM, provider)
cryptor.setKeyIndex(schedule.keyIndex)
cryptor.setEnabled(true)
```

Receiver (in `GroupSfuPeer`'s `onAddTrack`; map `streams`/track msid to the participant from the DO
`welcome`/`joined` roster, which carries pubkey+device+sessionId):

```kotlin
override fun onAddTrack(receiver: RtpReceiver?, streams: Array<out MediaStream>?) {
    val p = participantFor(streams ?: return) ?: return
    val cryptor = FrameCryptorFactory.createFrameCryptorForRtpReceiver(
        factory, receiver, p.frameCryptorParticipantId(), AES_GCM, provider)
    cryptor.setKeyIndex(schedule.keyIndex)
    cryptor.setEnabled(true)
    // keep it next to the remote track and dispose it with the track
}
```

Verify the positional arguments against `javap` from the WP02 evidence before merging; the API in
`io.github.webrtc-sdk:android:144.7559.15` exposes no encoded transform, so this is the only Android hook.
Unknown/retired epoch is handled by `discardWhenNotReady = true` (no key → `MISSINGKEY`, no audio). Android
cannot call `GroupCallReplayGuard` per frame because `FrameCryptor` gives no frame callback — see "Not done".

### Desktop — `DesktopSfuPeer` (`webrtc-java` encoded transforms)

Maintain `sessionId -> ParticipantDevice` from the room welcome/joined events and an
`epochKeys = schedule.keyRing()` plus one `GroupCallReplayGuard` per call. Never install a transform that
returns the original bytes on failure; `drop()`.

Send, where `publish()` currently does `n.sender = n.connection.addTrack(track, ...)`:

```kotlin
val sender = n.connection.addTrack(track, listOf("relay"))
val myKey = schedule.aesKeyFor(me)
sender.setTransform { frame ->
    val sealed = GroupFrameCrypto.seal(frame.data, epochKeys.keyIndex, myKey, GroupFrameCrypto.newIv())
    if (sealed is FrameSealResult.Sealed) frame.setData(sealed.frame) else frame.drop()
}
```

Receive, where `reconcile()` binds `t.receiver` and adds the PCM sink:

```kotlin
receiver.setTransform { frame ->
    val sender = participantFor(ref.sessionId) ?: return@setTransform frame.drop()
    val opened = GroupFrameCrypto.open(frame.data, sender, epochKeys)
    if (opened !is FrameOpenResult.Opened) return@setTransform frame.drop()
    if (replay.admit(sender, epochKeys.epoch, frame.ssrc, frame.sequenceNumber) != ReplayDecision.ACCEPTED) {
        return@setTransform frame.drop()
    }
    frame.setData(opened.plaintext)
}
```

After `rotateForRemoval`, install a new `epochKeys`, call `replay.removeEpochsBelow(newEpoch)`, recreate
`GroupCallE2eeStatus.forSchedule(newSchedule)`, and dispose the old provider/cryptors on Android.

### UI label

```kotlin
val status = GroupCallE2eeStatus.forSchedule(schedule)
// own device: only after its cryptor/key install succeeded and it is sealing
status.verify(me, epochKeys.epoch)
// on every inbound frame that authenticated at the current epoch:
status.verify(sender, epochKeys.epoch)
// never call verify with a value from the wire; use the epoch the frame actually opened with
banner.text = status.label(
    allParticipantsCapable = rosterDevices.all { it.supportsFrameE2ee },
    keyDistributionAuthenticated = inviteOpenedThroughE2eSeal,
    sendPathEncrypted = e2eeActive && cryptorsEnabled,
)
```

`isEndToEnd` requires exact equality between expected devices and verified devices, every verified epoch ==
current epoch, non-empty roster, capability, authenticated key distribution, and a sealing send path. A
silent participant is therefore not verified; the label stays "encrypted in transit, not end to end".

## Not run / not done

- **No live SFU, emulator, physical device or macOS run.** WP17-AC1/AC2 are not met and no interop claim is
  made. The fixed vector proves only that the Kotlin derivation matches an independent implementation.
- Android frame-level replay protection remains impossible with the Java `FrameCryptor` API (no transform, no
  per-frame sequence callback). The guard exists and is wired only on the desktop side; closing this needs a
  native/NDK hook or an API from `io.github.webrtc-sdk:android` that is not present in 144.7559.15.
- The Android integration above is a compile-unchecked snippet: the exact `createFrameCryptorKeyProvider`
  parameter list and whether `uncryptedMagicBytes` accepts `null` were not compiled on this host (no Android
  build in this task). Verify with `javap` before use.
- `group_start` still cannot carry `e2eeKey`/`keyEpoch` from the existing core codec; no key distribution over
  Relay's E2E channel was wired, by ownership rule. A host must extend that existing codec.
- Zero-length frames: our open rejects them; desktop must drop rather than forward. Android `FrameCryptor`
  still passes them in clear before any of our code runs — harmless (no audio) but documented.
- No key zeroization after rotation; ByteArray copies live until GC. No ratchet-window/SIF magic-byte support.
- Only 2-participant/1-device vectors and unit tests; no 3+ party, no device-per-member matrix, no DTX/frame
  loss simulation beyond the 1-byte DTX round trip.
