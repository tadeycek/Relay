# 03. Decisions

> Read [10-readiness-gates.md](10-readiness-gates.md) before implementation. It corrects security, lifecycle and
> compatibility assumptions below and takes precedence where the initial proposal conflicts with a gate.

IDs use the `LP-D` prefix so they don't collide with the decisions in `rebuild/`. The owner settled the scope in
chat on 2026-10-23: same server, local-only storage, files are the priority, 1:1 calls, and group calls on option A
(Cloudflare SFU). The rows below record the decisions that follow from that scope.

| ID | Decision | Rationale | Trade-off accepted |
|---|---|---|---|
| LP-D01 | The desktop is a **new client on the existing protocol**, not a port of the Android UI. | 93 of 186 files are Android-bound: Keystore, WorkManager, FCM, CameraX, SMS, the launcher disguise. The protocol is the part that has to stay identical. | The desktop UI and storage are rewritten. Only the protocol code is shared. |
| LP-D02 | **Linked device with a shared identity, plus per-device cursors on the server.** It replaces the "separate device key, senders fan out" model discussed earlier in chat. | Fan-out would need every contact's phone and every group roster to learn about devices: an app update for everyone, roster v3, and twice the inner encryption. With a shared identity, peers change nothing, and only our server and our own clients change. The server already authenticates by key, and the `u` tag signs query parameters. | A desktop holds the full identity (nsec and Tink keys). Stealing a linked desktop is as bad as stealing the unlocked phone. True revocation means a new identity (see 09 R3). |
| LP-D03 | **The phone is primary.** Only the phone pairs contacts, rotates Tink keys, links or unlinks computers, and creates or edits group rosters. Desktops mirror these actions through sync events. | One writer per kind of state means no conflict resolution. The phone already owns rotation, PIN wipe and QR pairing. | The desktop can't add a contact by itself. It shows "pair on your phone". |
| LP-D04 | **Kotlin, Compose Multiplatform Desktop and a shared `:core` JVM module.** | The same language as the app. `nostr-sdk-kmp-jvm` 0.44.8 matches the phone's version exactly. Tink and `MediaCrypto` are pure JVM. Compose skills carry over. Option A (the SFU) needs only plain WebRTC, and `webrtc-java` covers Linux. | The bundled JVM makes the install about 150–200 MB. Rust/Tauri would be lighter but would duplicate all the logic. |
| LP-D05 | Desktop secrets: a **database key and identity bundle sealed with a key held in the OS secret store** behind one `SecretStore` interface. Linux uses the Secret Service (GNOME Keyring/KWallet). macOS uses the Keychain. Both go through `java-keyring` unless WP06 finds a blocker. There is an **optional app passphrase** (Argon2id), which is required when no secret store is available. | The OS keyring is unlocked at login and needs no extra friction. One interface keeps `:core` and the UI platform-free. The passphrase covers headless or bare window-manager setups and users who want a lock. | Anyone with the user's unlocked session can open Relay unless a passphrase is set. That is the same as most desktop messengers. On unsigned macOS builds the Keychain may prompt again after each update. |
| LP-D06 | **No history backfill when linking.** Linking copies identity keys, contacts, groups and settings, but no messages or media. | Keeps the link bundle small (≤128 KiB) and avoids a bulk phone-to-desktop export path. Phones only keep 7 days anyway. | A new desktop starts with empty chats. |
| LP-D07 | **Files are a new `TYPE:FILE` body**, up to **100 MiB**, split into **parts of 26,212,814 plaintext bytes (stored blob ≤ 25 MiB + 64)**. Each part is a versioned raw `/v1/media` object encrypted with a new per-file key and a fresh random per-part IV. The authenticated manifest carries a mandatory full plaintext SHA-256 and binds its file id to `RelayPayload.id`. Empty files use one authenticated empty part. | Keeps the server's per-object limit and frozen planning constants. Private disk staging avoids simultaneous app blob/plaintext arrays; JCA provider buffering and Android peak heap still require measurements. Completed ciphertext retries unchanged. | Up to 5 objects per file, so about 5× the recipient rows. Older 1.15 builds show "unsupported message, update Relay". |
| LP-D08 | **Desktop retention matches the phone: 7 days**, using the same `RetentionPolicy`. Files the user explicitly saved are exempt (they leave Relay's store). | It's the existing privacy promise, and the server refuses nothing older anyway. | Desktop history isn't an archive. A per-device setting can come later. |
| LP-D09 | **1:1 calls are peer-to-peer WebRTC audio.** Signalling runs over mailbox socket `signal` frames, plus one stored `CALL_INVITE` that wakes the callee. Cloudflare STUN is used, with TURN as fallback. | DTLS-SRTP runs end to end between the two devices, and TURN only relays ciphertext, so the calls stay E2EE. There's no SFU cost, and the media server is used only when needed. | Two call paths to maintain (P2P and SFU). The 1:1 code is reused for group control where possible. |
| LP-D10 | **Ring every device** of the callee's identity. The first device to accept wins, and the others get `CALL_ANSWERED_ELSEWHERE` through a self-signal. | Matches what users expect from Discord or WhatsApp desktop. | The callee's devices race. The protocol has to handle duplicate answers (06 §4). |
| LP-D11 | **Group calls use Cloudflare Realtime SFU** (option A), with a `CallRoom` Durable Object per active call and the Worker proxying the SFU API. | No participant cap from the design, $0 at this scale (02 §E), no homelab dependency, and the same Cloudflare account and deploy flow. | The SFU terminates DTLS-SRTP, so Cloudflare could hear group audio until WP17. Room logic is our code. |
| LP-D12 | **Group call authorisation uses capability tokens.** The call starter mints a random `roomId` and `joinSecret`. The invitation travels E2E to the members. The DO stores only `sha256(joinSecret)` and checks NIP-98 server membership. | The server doesn't know group rosters (they live on clients, E2E) and shouldn't learn them. | A member who leaks the secret lets another server member join. The roster check on clients flags unknown participants (07 §5). |
| LP-D13 | **CallRoom state lives in hibernatable WebSocket attachments plus at most one row per participant.** The DO is deleted when it empties. | Keeps rows written near zero and survives hibernation. | Losing the DO (rare) ends the call; clients rejoin automatically. |
| LP-D14 | Server changes stay **backward compatible**. A missing `device` parameter means device `"primary"`, so phones on 1.15 keep working unchanged. | Contacts update at different times. | A primary phone on 1.15 can't link a desktop until it updates. |
| LP-D15 | **Desktop packaging is `.deb` (jpackage via Compose) plus an AppImage** built from the same app image, with SHA-256 sums and provenance, following `rebuild/DISTRIBUTION.md` practice. Linux x86_64 only. | Covers Ubuntu (the owner's machine) and most other distros. | No Flatpak or auto-update in this plan. |
| LP-D16 | **Group call E2EE (WP17) is planned but gated.** Frame encryption uses a per-call key from the E2E invite, AES-GCM on encoded frames through Android `FrameCryptor` and webrtc-java encoded transforms. It ships only if the WP02/WP17 spike proves both platforms produce one interoperable frame format. | Keeps calls at parity with Relay's E2E promise without blocking the group call release. | Until it ships, the group call UI says "Group calls are encrypted in transit, not end to end." |
| LP-D17 | **macOS ships as an unsigned `.dmg` for Apple Silicon**, built by a GitHub Actions macOS runner from the same desktop module. It has no Apple Developer account, no notarization and no App Store. Intel Macs aren't built or tested. | The owner wants Mac support without App Store or Apple fees. The code is identical. Only the secret store, the Info.plist keys and the build host differ. | Gatekeeper's "Open Anyway" step on first launch. Permission prompts may repeat after updates. Mac testing depends on someone with a Mac (09 Q6). |
